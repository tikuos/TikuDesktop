# Architecture notes — List columns, count view, settings

Read from the real source; structural facts the rewrite must
reproduce for this area.

OWNERSHIP / DATA FLOW. BColumn objects are owned by BPoseView (fColumnList) and carry the authoritative geometry (fOffset, fWidth), identity (fAttrName + fAttrType + fAttrHash where hash = AttrHashString(name,type)) and policy flags (fAlignment, fStatField, fEditable, fDisplayAs). BTitleView owns a parallel list of BColumnTitle wrappers (fTitleList) that store no geometry at all — BColumnTitle::Bounds() is computed from the column's offset/width every time (left = offset - 11, right = left + width + 16). Therefore any code that changes a column's offset/width must simply Invalidate the title view; there is no second copy to keep in sync. The two lists are kept aligned only through BTitleView::Reset() (rebuild all), AddTitle(column, after) and RemoveTitle(column), all called from BPoseView's AddColumn/RemoveColumn/AddColumnList/RestoreColumnState. Column re-layout is always "recompute every offset from StartOffset() in list order", never incremental patching (see ResizeColumn and MoveColumnTo); AddColumn/RemoveColumn are the exceptions and shift only the tail by width+kTitleColumnExtraMargin.

CONSTANTS THE LAYOUT DEPENDS ON (TitleView.h): kEdgeSize 6 (resize grab zone, symmetric about the right border), kTitleColumnLeftExtraMargin 11, kTitleColumnRightExtraMargin 5, kTitleColumnExtraMargin 16, kMinColumnWidth 20, kRemoveTitleMargin 10 (vertical hysteresis before a dragged column is torn out); kRoomForLine 2 in PoseView.cpp participates in every offset formula.

TRACKING STATE MACHINE. BTitleView holds at most one ColumnTrackState (fTrackingState), created in MouseDown and deleted in MouseUp; MouseMoved delegates to it and does nothing else while it exists. The base class alone decides click-vs-drag: Clicked() iff released within press-time + get_click_speed() and never moved (1px slack while inside the click window), else Done(). ColumnResizeState mutates width; ColumnDragState mutates order or removes/reinstates the column, keeping a BMallocIO archive of the torn-out column so it can be restored byte-identically. Mouse capture uses B_NO_POINTER_HISTORY | B_LOCK_WINDOW_FOCUS. Two pieces of state persist across gestures on the title view itself: fPreviouslyClickedColumnTitle and fPreviousLeftClickTime, which is how double-click-on-edge (resize-to-widest) is detected.

DRAWING. All title drawing funnels through BTitleView::Draw(rect, useOffscreen, updateOnly, pressedColumn, trackRectBlitter, passThru); tracking feedback (press highlight, drag outline) is expressed as arguments to that one call, rendered into a single process-wide static OffscreenBitmap (BTitleView::sOffscreen) and blitted, which is what keeps drag/resize flicker-free. The offscreen frame is widened (frame.right += frame.left) to survive horizontal scrolling. The pose-view guide line during a resize is drawn/erased through function pointers (_DrawLine/_UndrawLine) passed into BPoseView::ResizeColumn, because the line lives in the pose view but the gesture lives in the title view; the erase path must re-tint for read-only volumes.

SORT AUTHORITY. Title clicks never sort anything themselves: they call BPoseView::SetPrimarySort/SetSecondarySort/SetReverseSort (which validate against ColumnFor(hash) and also record the attribute *type* into BViewState) and then SortPoses(). Sorting is std::stable_sort over fPoseList (and fFilteredPoseList when filtering) using PoseCompareAddWidget, which lazily creates missing text widgets, compares primary, and only on a tie retries once with the secondary key. Reverse sort swaps the operand pair rather than negating the result, preserving stability. Invariant enforced in several places: primary sort hash must name an existing column, and secondary must never equal primary (forced to 0).

THREADING. Directory reads run on a spawned "add poses" thread (BPoseView::AddPosesTask) that locks the window around every touch of the view; that thread is why BPoseView::ShowBarberPole/HideBarberPole take AutoLock<BWindow> and why every early-out path in the reader must call HideBarberPole. BCountView is B_PULSE_NEEDED: the barber pole animates from Pulse(), while StartBarberPole only arms a deadline (system_time() + kBarberPoleDelay = 500ms) so short reads never flash it. Count reconciliation is pull-based: BPoseView::UpdateCount -> BCountView::CheckCount compares cached fLastCount/fLastCountSelected and invalidates only the text sub-rect.

COUNT VIEW MODES. Three mutually exclusive display states with a fixed precedence in BCountView::Draw: type-ahead (non-empty fTypeAheadString) > filtering (non-empty fFilterString) > counts. Type-ahead string is transient and owned by the pose view's static sMatchString plus a BMessageRunner (kCheckTypeahead) that clears it after 2x get_click_speed(); the filter string mirrors the pose view's fFilterStrings list (multiple OR-terms separated visually by "|"), and the pose view is the one that adds/removes characters. Truncation direction differs per mode (beginning / middle / end) and is user-visible.

PERSISTENCE MODEL. Per-folder state is not in the settings file: columns and view state are archived as raw streams into node attributes (_trk/columns, _trk/viewstate, with _be/_le variants and separate names for the Desktop and the Disks/root window), written through AttributeStreamNode::Write which emits both endian names. Every archive carries AttrHashString(classname, B_OBJECT_TYPE) as a key plus a version: columns accept version >= kColumnStateMinArchiveVersion (21) with current kColumnStateArchiveVersion 22, view state must match kViewStateArchiveVersion (11) exactly. Offsets/widths are stored divided by (be_plain_font->Size()/12) and scaled back on load. Restored columns are order-repaired by sorting on stored offset and then re-laid out contiguously. Dirty tracking is two-part: BPoseView::fStateNeedsSaving (set by resize/reorder/add/remove) OR BViewState::StateNeedsSaving(), which compares every field against a shadow copy refreshed at construction and at each archive.

SETTINGS MODEL. One process-wide TTrackerState singleton (static gTrackerState) derived from the generic Settings/SettingsArgvDispatcher framework; BPrivate::TrackerSettings is a stack-constructed façade whose constructor triggers LoadSettingsIfNeeded, so any code can write "TrackerSettings().Foo()" cheaply. Each setting object knows its own default (all defaults centralised in TrackerDefaults.h) and serialises itself; SaveSettings(true) writes only non-defaults, SaveSettings(false) writes everything, and saving rewrites the file wholesale after deleting it. Settings changes propagate on two channels simultaneously: the singleton is updated directly, and TTracker::SendNotices broadcasts a BMessage that pose views and container windows receive as B_OBSERVER_NOTICE_CHANGE and re-apply (pose views deliberately re-set the setting from the notice so file panels hosted in other teams converge). Preferences views follow a fixed four-method contract — ShowCurrentSettings (pull model into widgets), RecordRevertSettings (snapshot for Revert), IsDefaultable/IsRevertable (button + bold-label state), SetDefaults/Revert — and every mutation posts kSettingsContentsModified to the window, which re-saves and recomputes button state.
