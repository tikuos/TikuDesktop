# Architecture notes — PoseView: keyboard navigation, type-ahead, shortcuts, scripting

Read from the real source; structural facts the rewrite must
reproduce for this area.

THREADING / OWNERSHIP. BPoseView is a BView inside BContainerWindow; KeyDown, MessageReceived, all scripting handlers and all TShortcuts::Update* code run on the window's looper thread with the window locked. Nothing in this area is re-entrant or ISR-like. The only asynchrony is (a) the BMessageRunner fKeyRunner posting kCheckTypeahead to self at the double-click interval, and (b) MoveListToTrash(), which takes ownership of a heap BObjectList<entry_ref> and frees it on a separate trashing thread.

THREE POSE LISTS, ONE ACCESSOR. fPoseList = every pose in sort order; fFilteredPoseList = the subset surviving type-ahead/ref filtering (list mode only); fVSPoseList = icon-mode visual ordering. CurrentPoseList() returns fVSPoseList outside list mode, else fFilteredPoseList when IsFiltering() else fPoseList; CountItems(), IndexOfPose(), PoseAtIndex() and all keyboard navigation go through it. IsFiltering() = IsRefFiltering() (a BRefFilter is installed, file panels) OR IsTypeAheadFiltering(). Two functions deliberately do NOT use it: FindBestMatch and FindNextMatch scan fPoseList and return fPoseList indices - correct only when unfiltered, and the returned index is then fed to SelectPose(). Reproduce or consciously fix, but know it is there.

NO FOCUS CURSOR. There is no separate "focused pose". The keyboard cursor is fSelectionList->LastItem() for arrows, and fSelectionList->FirstItem() for Page Up / range extension and Edit name. fSelectionList is insertion-ordered, so selection order is load-bearing. Two anchors exist: fSelectionPivotPose (Shift-extension anchor) and fRealPivotPose (saved during rubber-band drags); ClearSelection(), SelectAll(), InvertSelection(), SelectPoses(start,end) and RemovePoseFromSelection() all null or reset them, and AddRemovePoseFromSelection() refuses a no-op toggle.

INDEX ARGUMENT IS LIST-MODE-ONLY. SelectPose/AddPoseToSelection take (pose, index); index reaches CalcPoseRect(), which uses it only in list mode (CalcPoseRectList: y = index * fListElemHeight) and ignores it in icon modes (CalcPoseRectIcon uses the pose's stored location). This is why FindNearbyPose never assigns *poseIndex on the icon-mode paths.

TYPE-AHEAD IS TWO DISTINCT MECHANISMS SHARING ONE KEY PATH. (1) Type-ahead SELECT: static sMatchString + per-view fLastKeyTime, coalescing window = get_click_speed() * 2, scoring via ComputeTypeAheadScore with wordMode=false, feedback in BCountView::SetTypeAhead. (2) Type-ahead FILTER: BObjectList<BString> fFilterStrings (always at least one element, seeded in the constructor), gated on list mode AND the TrackerSettings TypeAheadFiltering flag, feedback via BCountView::AddFilterCharacter/RemoveFilterCharacter/CancelFilter. Backspace, Escape, Return and Tab all branch on IsTypeAheadFiltering() first. Incremental narrowing vs. full rebuild is decided by comparing fLastFilterStringCount/fLastFilterStringLength with the current term count/length - those two shadow fields are the whole state machine.

KEY DISPATCH ORDER (highest priority first). 1) Window shortcuts registered with BWindow::AddShortcut - these imply B_COMMAND_KEY unless B_NO_COMMAND_KEY is passed, and they consume the key before any view sees it. 2) Common message filters on the window (file panel key_down_filter, OpenWithContainerWindow::KeyDownFilter). 3) View-level ShortcutFilters added in BPoseView::AttachedToWindow (Option+Return, Escape, Shift+Escape) - ShortcutFilter::Filter compares modifiers for EXACT equality after masking to Shift/Command/Control/Option/Menu, so lock keys are ignored and extra modifiers break the match. 4) TextViewKeyDownFilter when a name is being edited (Return/Escape/Tab never reach the pose view). 5) BPoseView::KeyDown. 6) _inherited::KeyDown (only for Tab in file panels). BPoseView::MessageReceived checks HandleMessageDropped() then HandleScriptingMessage() before its own switch.

MENU/SHORTCUT STATE IS RECOMPUTED, NOT CACHED. TShortcuts holds only a BContainerWindow* and an fInWindow flag; the "dumb" default-constructed instance can build items but its Update methods skip everything guarded by fInWindow. Every label/command/enable decision reads live global state (modifiers(), selection, volume read-only, Trash/root/query/virtual-dir predicates) at Update() time - called from MenusBeginning. Shift-variant items MUTATE the existing BMessage's `what` in place and re-set the item's shortcut modifier mask, so one menu item alternates between two command codes; anything matching on `what` must accept both (TShortcuts::Update's switch and TShortcuts::FindItem(menu, cmd1, cmd2) both do).

SCRIPTING CONTRACT. Suite "suite/vnd.Be-TrackerPoses"; three properties (Path, Entry, Selection) plus two custom specifier forms kPreviousSpecifier='sprv' / kNextSpecifier='snxt' and B_ENTRY_SPECIFIER='sref' (Tracker.h). HandleScriptingMessage returns bool: true means it replied and consumed the message, false means fall through - so an unmatched property never produces a reply. Errors travel as an "error" int32 inside the B_REPLY. Actions that affect files never execute inline: they are posted to fSelectionHandler (a BLooper*, defaulting to be_app, overridable via SetSelectionHandler - file panels retarget it), with a "TrackerViewToken" BMessenger(this) embedded so the launched application can script back into the originating view. Index-based addressing is explicitly documented as best-effort and every index path must degrade to B_BAD_INDEX / B_ENTRY_NOT_FOUND rather than fault.

TIKU-WIDE DECISIONS THIS AREA FORCES. (1) get_click_speed() has no TikuOS analogue - the type-ahead coalescing window and the fKeyRunner period must become explicit configuration, not a borrowed UI constant. (2) "Column text" that type-ahead and the filter match against becomes typed descriptor fields of a namespace node; which fields participate, and in what order, is a decision the rewrite must make explicitly (the original tries columns left to right and stops at the first that scores). (3) Filtering must be re-evaluated on watch notifications, since a device node's value can change without any add/remove and can move the node in or out of the filter. (4) Read-only-volume predicates (SelectedVolumeIsReadOnly / TargetVolumeIsReadOnly) map to per-node capability bits, so enablement becomes per-selected-node rather than per-volume. (5) There is no Trash for device nodes - both the Delete key path and 'delete Entry' scripting need a defined destructive verb.
