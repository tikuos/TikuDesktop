# Architecture notes — PoseView: node monitoring and live updates

Read from the real source; structural facts the rewrite must
reproduce for this area.

DATA FLOW. The kernel node monitor (and BPathMonitor, and query notifications) deliver BMessages to the BPoseView BHandler. BPoseView::MessageReceived funnels three what-codes -- B_NODE_MONITOR, B_PATH_MONITOR, B_QUERY_UPDATE -- into ONE virtual entry point, bool BPoseView::FSNotification(const BMessage*). FSNotification switches on the int32 "opcode" field and fans out to EntryCreated / EntryMoved / DeletePose / AttributeChanged / volume handling. Subclasses (BQueryPoseView, VirtualDirectoryPoseView) override FSNotification or AttributeChanged and delegate to _inherited. Message field names are load-bearing and differ per opcode: created/removed use device+node+directory+name; moved uses device + "node" + "from directory" + "to directory" + "name" (and, in the path-monitor variant the virtual-dir view parses, "node device" + "from name" + "path" + "from path"); stat/attr use device+node plus "attr" (string) or "fields" (int32 stat-field mask).

THE FALSE-RETURN CONTRACT. FSNotification returns bool. false means "this named a node I do not know about yet". MessageReceived then copies the entire message into `pendingNodeMonitorCache` (a PendingNodeMonitorCache member of BPoseView, PoseView.h:720). Entries live 10 s (kDelayedNodeMonitorLifetime) and are replayed verbatim through FSNotification by PendingNodeMonitorCache::PoseCreatedOrMoved once the matching pose materializes. This is the ONLY out-of-order repair mechanism; there is no coalescing anywhere in the node-monitor path (the only accumulation in the file is MetaMimeChangedAccumulator, and that is for B_META_MIME_CHANGED, not node monitoring). The rewrite must reproduce: notifications are applied in arrival order, one at a time, and a notification for an unknown node is deferred rather than dropped.

THREADING. Three actors touch pose state. (1) The window thread runs MessageReceived/FSNotification with the BWindow locked by the message loop. (2) A detached "add poses" thread (BPoseView::AddPosesTask, spawned at B_DISPLAY_PRIORITY from BPoseView::AddPoses) reads dirents and constructs Models with the window UNLOCKED, then re-locks per chunk via AutoLockingMessenger and ships the chunk as a kAddNewPoses message carrying a raw AddPosesResult* pointer. Poses are actually created only on the window thread, in CreatePoses. (3) Background TaskLoop entries (ContainerWindow()->DelayedTaskLoop(), tracker->MainTaskLoop()) run delayed work -- TryUpdatingBrokenLinks 500 ms after a mount, MetaMimeChanged after 200 ms, dynamic-date query Refresh at the next minute/hour/midnight -- each re-locking the window. fAddPosesThreads is a std::set<thread_id> of "blessed" loader threads; clearing it (SwitchDir, DetachedFromWindow, BQueryPoseView::Refresh) is how a stale loader is told to die, and the loader checks IsValidAddPosesThread() every chunk while holding the lock. DetachedFromWindow drops the lock and wait_for_thread()s every loader before returning.

OWNERSHIP. Model objects are created by the loader thread or by EntryCreated and ADOPTED by BPose in CreatePoses; the pose deletes its model. A chunk that is discarded (wrong ref, duplicate node, zombie) deletes the Model and calls watch_node(..., B_STOP_WATCHING). AddPosesResult::~AddPosesResult deletes any models still owned; ReleaseModels() nulls the array after a successful hand-off. Models that fail InitCheck live in fZombieList (owning). Broken symlink Models live in fBrokenLinks (NON-owning -- they are also owned by their poses).

INVARIANTS THE CODE RELIES ON.
 - Watch first, read second. WatchNewNode is called on a node BEFORE the Model is constructed, in both AddPosesTask and EntryCreated, precisely so a change racing model construction still produces a notification. This is the core anti-staleness rule.
 - One pose per node_ref. Enforced twice: EntryCreated rejects if fPoseList->FindPose or FindZombie hits, and CreatePoses rejects if fInsertedNodes (a node_ref set) already contains it. fInsertedNodes is cleared in SwitchDir and Refresh and pruned in DeletePose. This is what keeps a node-monitor create racing the bulk loader from producing a duplicate row.
 - Watch masks are set once per directory, not per entry. BPoseView::InitDirentIterator installs B_WATCH_DIRECTORY|B_WATCH_CHILDREN|B_WATCH_NAME|B_WATCH_STAT|B_WATCH_INTERIM_STAT|B_WATCH_ATTR on the target; WatchNewNodeMask() returns 0 for plain dirs and queries because B_WATCH_CHILDREN / B_QUERY_WATCH_ALL already covers children. Per-node watches exist only where the container cannot cover it: symlink targets outside the dir, volume poses on the Desktop, the Trash icon, and OpenWithPoseView (which returns B_WATCH_STAT|B_WATCH_INTERIM_STAT|B_WATCH_ATTR).
 - stop_watching(this) is the universal teardown -- BPoseView::StopWatching drops every watch the handler holds in one call, so SwitchDir/Refresh must re-establish ALL of them (mount watch, target attr watch, dir watch via the iterator, symlink parents).
 - Sort order is repaired incrementally, never by full re-sort: _CheckPoseSortOrder pulls the pose out of the list, BSearches its new home, and blits the gap. It runs only in kListMode and only when the changed attribute hashes to the primary or secondary sort key.
 - Node-monitor slots are a finite kernel resource; TTracker::WatchNode retries once after raising RLIMIT_NOVMON by 512 (NeedMoreNodeMonitors). Every watch in Tracker goes through this wrapper rather than raw watch_node, except the stop-watching calls.
 - Filtering is a second, derived list (fFilteredPoseList). Every notification handler that can change visibility must ask FilterPose() again and add/remove from the filtered list independently of the master list, keeping two indices (poseListIndex into fPoseList, index into the visible list).
