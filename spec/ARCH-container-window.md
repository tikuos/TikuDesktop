# Architecture notes — ContainerWindow: window behavior, menus, navigation

Read from the real source; structural facts the rewrite must
reproduce for this area.

OWNERSHIP / THREADING
- Every folder window is its own BWindow (own thread + message loop). All code below runs with the window locked; `ShowContextMenu` ASSERTs `IsLocked()`. Cross-window work (close-all, open-ref, duplicate-window detection) goes through the app object (`be_app`/TTracker) which owns `fWindowList` (a `LockingList<BWindow>`) that each window adds itself to in the ctor and removes itself from in `Quit()`.
- `BContainerWindow` owns exactly one `BPoseView` (`fPoseView`, created by `CreatePoseView()`/`NewPoseView()`, which subclasses override: BQueryContainerWindow -> BQueryPoseView, BDeskWindow -> DesktopPoseView, VirtualDirectoryWindow). `TargetModel()` is just `PoseView()->TargetModel()` - the window has no model of its own. Nearly every menu item's target is either the PoseView, the window, or `be_app`; `TShortcuts::Update*` sets both the enabled state and the target on every menu open.
- View tree when `fUsesLayout` (everything but Desktop): root BGroupLayout(vertical) -> fMenuContainer (menu bar + DraggableContainerIcon side by side) -> fPoseContainer (BGridView): row 0 col 0 span 2 = BNavigator, row 1 col 0 = BorderedView(PoseView + TitleView), row 1 col 1 = vertical scrollbar container, row 2 = fCountContainer (CountView + horizontal scrollbar). Desktop passes `useLayout=false` and adds the pose view directly.
- Menus are BUILT ONCE (`AddMenus`, `AddContextMenus`) and MUTATED IN PLACE on every open. A set of shared, detachable items lives on the window and is re-parented between the File menu and the pose context menu: fMoveToItem, fCopyToItem, fCreateLinkItem, fOpenWithItem, fEditQueryItem, fMountItem, fNavigationItem, fNewTemplatesItem, fArrangeByItem, fAttrMenu. Invariant: an item is in at most one menu at a time; `Setup*` removes it from its old menu first, `DetachSubmenus()` detaches all, `Quit()` deletes only those with `Menu() == NULL`. Separators added next to a shared item must be removed with it (see SetupMoveCopyMenus / SetupNavigationMenu / DetachMountMenu).
- Menu items are located by MESSAGE COMMAND, not by index or label (`menu->FindItem(kOpenSelection)`, `TShortcuts::FindItem(menu, kCleanup, kCleanupAll)`), then items are inserted at `IndexOf(anchor) + n`. A rewrite must keep stable command ids as the anchor mechanism or reproduce an equivalent named-slot scheme.
- Menu update runs in three places and they must agree: `MenusBeginning()` (mouse or key open of the menu bar), `ShowContextMenu()` (before a popup `Go()`), and the LiveMenu `Update()` hook (B_MODIFIERS_CHANGED arriving while the menu is already open). All three funnel through `UpdateMenu(menu, context, ref)` / `TShortcuts::Update*`.
- Slow menus (BNavMenu, FavoritesMenu, RecentsMenu, MountMenu, TemplatesMenu) build lazily from the menu-tracking thread via `AddDynamicItem`, 20 items or 200 ms per chunk (SlowMenu.cpp), so directory enumeration never blocks the window thread. `fMenuBuilt` is reset by `ClearMenuBuildingState()`/`ForceRebuild()` so a menu re-enumerates each time it is opened.
- Window state is a stream of BFS attributes on the folder's own node, wrapped by `WindowStateNodeOpener` (root/"Disks" redirects to the Desktop directory). `AttributeStreamNode` chaining (`<< transformer << memoryNode << filter << fileNode`) is how defaults are copied and mutated. Attribute names: kAttrWindowFrame, kAttrWindowWorkspace, kAttrWindowDecor (kAttrDisksFrame/kAttrDisksWorkspace for root).
- `fStateNeedsSaving` is set only when the window is ACTIVE (FrameResized/FrameMoved/WorkspacesChanged), OR'd with `PoseView()->StateNeedsSaving()`; state is written in `Quit()` and in `SwitchDirectory()` before leaving a folder.
- The static `fAddOnsList` (LockingList<AddOnInfo>) is shared by ALL windows and is populated/owned by BDeskWindow (`InitAddOnsList`), which also node-monitors the add-on directories and broadcasts `kRebuildAddOnMenus` to every container window. Add-on code is loaded with `load_add_on` and run on a spawned thread (AddOnThread / RunAddOnMessageThread), never on the window thread.
- Navigation history lives per window in BNavigator (fBackHistory/fForwHistory, max 32 entries) and is mutated only through `UpdateLocation(model, action)`; the action code (kActionSet/Forward/Backward/Up/Location/UpdatePath) decides how the two stacks move. `SendNavigationMessage` deliberately unlocks the looper around `TTracker::SelectChildInParentSoon()` to avoid a lock-order deadlock with the task loop.
- Two navigation regimes share one class: SPATIAL (folder -> new window, message becomes B_REFS_RECEIVED to be_app with "nodeRefToSelect"/"nodeRefsToClose") and SINGLE-WINDOW-BROWSE (folder -> `SwitchDirectory()` in place). The mode is a global TrackerSettings flag; windows subscribe to kSingleWindowBrowseChanged / kShowNavigatorChanged / kWindowsShowFullPathChanged via `StartWatching` on the app and reconfigure themselves live.
- `PiggybackTaskLoop fTaskLoop` is driven by `BorderedView::Pulse()` -> `PulseTaskLoop()`; deferred work (delayed selection, etc.) is queued there rather than on a timer of its own.
