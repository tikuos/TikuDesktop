TikuConsole

TikuConsole is the desktop's serial console for a connected board. It is opened from Device Tools in the Deskbar leaf. Opening the application does not touch a serial port: it shows the boards this desktop has mounted and waits to be told which one to talk to.

Choosing a board

The list at the top of the window holds the boards mounted now. When the desktop's default device is one of them, it is already chosen as the window opens, and Open console acts on it straight away. When the board that was chosen is no longer there, the list is offered again and no other board is picked in its place.

Connecting a board, and setting which one is the default, is done from the Devices menu on the top bar. See Devices.

Open console

Open console asks the desktop to let go of the chosen board, and then opens that board's serial port for itself. The board's port and MCU are read before the desktop releases it, because neither can be read once the mount is gone. The statistics shown are the last set the desktop kept, and they stop being refreshed with the mount. The console opens the port only once the desktop has finished closing it, so the two never hold the cable at the same time.

The desktop refuses to let go of any board while a program is running on one of them. The status line then says that the device is busy or unavailable. Stop the other device work and press Open console again. If the desktop has not answered within ten seconds, the console gives up and asks for the board back.

What exclusive access means

Releasing a board takes its mount down. While TikuConsole holds the port:

  • /devices/<name> is not in the namespace, so a folder window on that board, and any file operation reading or writing through it, no longer finds it
  • any window the board itself publishes is closed with the mount
  • the Device Monitor and the VFS Inspector read a board through its mount, so a board the console holds is not there for them to read
  • the board list and the baud setting are locked, so the port cannot be changed under the connection
  • the figures on the Device tab are the snapshot taken before the release, not live readings

Two owners on one serial port corrupt each other's traffic, so the desktop hands the board over whole or not at all.

Return to desktop

Return to desktop closes the console's own descriptor, discards input that has not been sent, and asks the desktop to take the board back. The desktop asks every serial port at once and mounts back the one whose identity matches the board that went. A different board is never mounted in its place.

When every port has answered and none of them had it, the status line says the handoff failed and to check Devices before retrying. When nothing has answered within fifteen seconds, it says the device did not return and to reconnect it through Devices. When the desktop will not take the request at all, which happens for a board this desktop never let go and while an earlier return is still under way, the status line says the device could not be returned and to reconnect it through Devices.

Finish any interactive program on the board before handing it back. A board that does not answer the request does not come back, and has to be connected again from Devices.

Files...

Files... opens /devices/<name>/data, the board's data folder, in the file manager. Pressed while the console holds the port, it performs the same handoff first and opens the folder once the board is back on the desktop.

Copying a file into that folder puts the file on the board. Copying one out brings a copy here and leaves the board's own file in place: a file can be copied off a board, but not moved off it, because nothing in the backend contract removes anything from a board.

The gesture is the ordinary one, with two limits. A folder cannot be copied between this machine and a board. A file larger than 64 KiB is refused, because files crossing between stores are read whole. When the file manager will not open the path, the path is put on the clipboard and the status line says so.
