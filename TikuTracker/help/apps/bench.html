TikuBench

View / Results report opens a formatted results snapshot in the Help reader. You can search the report and copy text. Long reports explicitly say how many result rows are shown; the full results and log remain in Bench. Opening a report never starts tests, flashes firmware or reconnects a device.

Bench runs TikuBench's test suites against a board connected to this desktop and shows what came back. The Deskbar leaf offers it under Device Tools as TikuBench. The window it opens is named Bench, and it puts two menus on the top bar: Bench, and a View menu whose rows are the seven tabs and, beneath them, Results report….

What it needs

The tests, the catalogue and the runner stay in TikuBench. Bench looks for a folder named TikuBench beside the applications folder this desktop was built in, and reads the catalogue by running TikuBench's own Python metadata reader there. Another checkout can be named outright with the TIKU_BENCH variable. With no checkout, or no Python behind it, the note line at the foot of the window says the metadata failed and Run selected stays disabled.

Refresh on the Suites tab, and Refresh catalogue in the Bench menu, read it again.

Choosing a device

Connect a board first from the Devices menu on the top bar, as Devices describes. The Device list at the top left of the window holds the boards mounted on this desktop. Before anything is chosen Bench uses the current device; once you pick a board it keeps that one, and a board that goes away is never silently replaced by another. Beside the list Bench prints the profile it will run under and either Monitor only or Build + flash.

Suites and tests

The Suites tab lists every suite in the catalogue with its sub-tests under it. The disclosure arrow or Return expands a suite; a checkbox or Space selects. The Filter field matches a suite's key, name and group and a sub-test's id and label, and while it holds text the matching children are shown expanded.

Selecting a whole suite runs that suite in full. Selecting sub-tests instead runs them as one --only argument. Selected suites run one after another in the order the catalogue lists them.

A suite the chosen board does not support is drawn dim and cannot be checked. When a suite is highlighted the line under the list shows its description. When a sub-test is highlighted it shows the sub-test's group and kind, then whether it belongs to a full sweep, is reachable only by selecting it, or why it is excluded. Select visible selects every displayed suite the board supports, each in full. Clear drops every selection, including those hidden by the filter. Changing the device, the memory model or the USB console setting also clears the selection.

Run options

The Run options tab holds five checkboxes and three fields.

  • Build + flash (off = monitor existing firmware only) is off when Bench starts. Off, the runner is told to skip the build. On, it builds and flashes, which replaces the firmware on the board. A test can still reset the board or write its storage either way.
  • MSP430 large memory model and RP2350 USB console (port and baud selected by runner) can be set only for boards whose catalogue entry allows them.
  • CRACEN public-key hardware: TIKU_CRACEN_PK_ENABLE=1 and ePaper kit: HAS_TIKUKITS=1, TIKU_KIT_EPAPER_ENABLE=1 add the make variables their labels name.
  • UART baud must be digits only, from 1200 to 4000000. A value outside that starts no run: the note line asks you to check baud, port and KEY=VALUE tokens, and the window returns to Run options. The field is disabled while the USB console is on, because the runner then finds the port itself.
  • Make variables takes whitespace-separated KEY=VALUE tokens with no shell quoting. A MEMORY_MODEL token is refused; use the checkbox.
  • Extra C flags is passed to the runner as one argument.

Options last as long as the window.

Running

Run selected is enabled only once the catalogue has loaded, the board is supported and something is selected. It opens a confirmation naming the number of suites, the device, the profile and the mode, and warning that the desktop will release its connection until the queue finishes. Its two buttons are Cancel and Run tests. Cancel is the default: Return takes the default and Escape cancels, so a run begins only when you move the default with Tab or press and release the pointer on Run tests.

On Run tests Bench checks that the device's port and MCU are still the ones named in the confirmation. If they changed, nothing runs and the note line says to select and review the device again. Otherwise the desktop hands the serial port over for the whole queue and the window changes to Results.

Results and output

  • Results lists a row for every planned test, then the counts of passed, failed and skipped groups and how many are complete. A test that asserted nothing is a skip, not a pass. A missing completion marker or a runner that exits badly is a failure.
  • Output is the test output with the build and flash lines, the lines carrying [TC:] completion markers and the runner's arguments taken out. Console is everything the runner printed, with the arguments each suite was started with. The two tabs share one ring of the latest 256 lines, which Output then filters; the whole run is in the log file. Scrolling with the wheel stops the view following, and Follow tail starts it again. Copy visible log copies the kept lines, and Clear view empties both Output and Console without touching the log.
  • The Input field and Send feed a line to a suite that asks for one, and work only while a run is under way. A suite that needs a board unplugged or reconnected says so in bold above the note line.
  • History and Benchmarks show the records TikuBench kept for the current profile. A full result older than 24 hours is marked stale. A benchmark comparison is not a test verdict.

Each run writes its own log under /tmp. Open full log opens it through the desktop, and copies its path when it cannot. A log worth keeping has to be copied out, because the system is free to clean /tmp.

Stopping and the device

Stop interrupts the runner and kills it if it has not gone two seconds later. Closing the window while a run is under way stops it first, then closes. When the queue ends the desktop takes the device back; if it does not return, the note line says to reconnect it in Devices.
