# Architecture notes — Application level: Tracker app, desktop, open-with, file panels, task loop

Read from the real source; structural facts the rewrite must
reproduce for this area.

OWNERSHIP AND THREADING (the invariants the rewrite must reproduce)

1. TTracker is a BApplication (signature kTrackerSignature) and owns, in construction order: the BPathMonitor WatchingInterface, gLaunchLooper (a separate BLooper), the Desktop window (created inside the constructor, before ReadyToRun), and BTrashWatcher. ReadyToRun then creates, in order: gStatusWindow, the MIME/index/template/background first-run installs, starts fTrashWatcher, creates and runs BClipboardRefsWatcher, creates the StandAloneTaskLoop (keepThread=true), creates the MimeTypeList, and finally (non-safe-mode) starts the transient-query cleaner and restores previously opened windows. The Desktop must exist before the trash watcher so the Trash icon is set; the task loop must exist before anything calls RunLater.

2. fWindowList is a LockingList<BWindow> owned by TTracker and shared with every window: BContainerWindow subclasses and BInfoWindow take it in their constructor and add/remove themselves (BInfoWindow adds itself in its ctor while Tracker holds the list lock, and removes itself in Quit; BContainerWindow::Quit removes container windows — Tracker's Close* helpers also remove entries, which the code itself flags as redundant). Every traversal asserts fWindowList.IsLocked(). Lock order is always WindowList first, then the individual BWindow (AutoLock<WindowList> then AutoLock<BWindow>) — see MoveRefsToTrash, SelectPoseAtLocationInParent, CloseActiveQueryWindows, the kUpdateThumbnail handler. Never the reverse.

3. Model ownership: TTracker::OpenContainerWindow hands the Model to the window ("window adopts model"); on the activate-existing path and the Open-With path it deletes the model itself. If CreatePoseView leaves PoseView() NULL the window posts B_QUIT_REQUESTED to itself. OpenWithContainerWindow adopts the refs BMessage (deleted in its destructor). BInfoWindow owns its Model and its BFilePanel.

4. Nothing that can block runs on a window thread. Three escape hatches exist and all three must survive: (a) gLaunchLooper, which executes a function pointer carried in a BMessage (AsynchLaunchBinder) so be_roster->Launch never runs on a window; (b) Thread::Launch for one-shot work such as LaunchAndCloseParentIfOK; (c) the TaskLoop worker thread for delayed/periodic/idle work. Synchronous TrackerLaunch is only legal when already on a spawned thread. BInfoWindow::CalcSize is a raw spawned thread with fStopCalc as its cancel flag, joined with wait_for_thread in BInfoWindow::Quit and before any restart; it locks the window before touching UI.

5. TaskLoop internals: fTaskList guarded by fLock (BLocker); Pulse() asserts the lock is held and removes tasks whose RunIfNeeded returned true; the worker thread is spawned lazily on the first AddTask and exits when the list drains unless KeepPulsingWhenEmpty(). The loop computes its own sleep deadline (min of earliest task time minus 1 ms and now+heartBeat), and AddTask pokes a sleeping thread via suspend/snooze(1000)/resume. PiggybackTaskLoop is the thread-free variant driven from a window's Pulse; file panels use it.

6. File panels run in the *client application's* team, not in Tracker. Therefore dynamic_cast<TTracker*>(be_app) is NULL inside a panel and every Tracker-only service must degrade: TTracker::WatchNode cannot bump the node-monitor limit, InitIconPreloader does not start the preloader, and BPoseView::OpenSelectionCommon does not add nodeRefsToClose. Cross-process coupling is done with BHandler::StartWatching on a BMessenger(kTrackerSignature) for setting-changed notices (kDesktopFilePanelRootChanged, kVolumesOnDesktopChanged, kHideDotFilesChanged, kTypeAheadFilteringChanged, ...). BFilePanel owns the TFilePanel window; when a client object is attached TFilePanel::QuitRequested hides instead of quitting, so lifetime belongs to the client.

7. Persisted state lives in two distinct places and the rewrite must keep the distinction: (a) per-object state written to the folder's own attributes (window frame, columns, view state) — unavailable on read-only/attribute-less volumes, which is exactly why the session message can carry state inline; (b) shared "template" nodes obtained via BContainerWindow::DefaultStateSourceNode under the Tracker settings directory, used for file panels (kDefaultFilePanelTemplate), the Open With window (kDefaultOpenWithTemplate) and the default query column sets. The session itself is one flattened BMessage in the kAttrOpenWindows attribute of the Desktop directory; "paths" strings are deduped but the per-path int8 flag can repeat (one entry per window on that path), and "window state" sub-messages are consumed in encounter order by a separate counter — so the two arrays are positionally coupled.

8. Node monitoring is funnelled through the static TTracker::WatchNode cover (retry after raising RLIMIT_NOVMON), and BPathMonitor is routed through TTracker::WatchingInterface so path watching uses the same cover. Several behaviors are driven by *synthesized* node-monitor messages rather than real ones (adding/removing the Disks icon on the desktop and in file panels) — the pose view's create/remove path is thus the single entry point for "an item appeared/disappeared", which the rewrite should preserve.

9. The Open With search is an iterator composition, not a list: SearchForSignatureEntryList concatenates a query walker over OR-ed kAttrAppSignature terms with a ConditionalAllAppsIterator that only yields while ShowAllApplications() is still true. The all-apps iterator MUST come last and the cached list must not be sorted, because CanOpenWithFilter both filters and mutates the "have we seen a real handler yet" flag as it goes — filtering is order-dependent. The same iterator object is shared by the pose view and its BRefFilter, so the pose view deliberately does not return/destroy it in ReturnDirentIterator.

10. The Desktop is a BContainerWindow subclass with the container chrome switched off (ShouldAddMenus/ShouldAddScrollBars/ShouldAddContainerView all false), and DesktopPoseView is reused as the root view of file panels via the shared static InitDesktopDirentIterator. Desktop pose locations are saved against fOldFrame (the pre-change screen frame) on every screen change and in the destructor, after which saving is disabled to keep quitting fast.

11. Message-level contracts other components depend on: "refs" (entry_ref list), "handler" (chosen app ref => Open With result), "launchUsingSelector" (int32 => run the Open With window), "nodeRefsToClose" / "nodeRefToSelect" (B_RAW_TYPE node_ref, index-parallel to refs), "TrackerViewToken" (BMessenger back to the originating pose view, used for scripting and for distinguishing panel messages that came from the pose view), and any "be:*" field which must be forwarded verbatim.
