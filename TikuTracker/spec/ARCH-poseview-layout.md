# Architecture notes — PoseView: view modes, layout, drawing, scrolling

Read from the real source; structural facts the rewrite must
reproduce for this area.

POSE LISTS AND OWNERSHIP. fPoseList (PoseList(40, true) — owning) holds every pose in the folder in sort order. Three non-owning lists alias into it: fVSPoseList (all poses sorted by y, used in icon modes), fFilteredPoseList (list-mode filtering) and fSelectionList. CurrentPoseList() returns fFilteredPoseList-or-fPoseList in list mode and fVSPoseList in icon modes (PoseView.h inline) — every draw, hit-test and selection loop goes through it, so index semantics differ per mode. INVARIANT: fVSPoseList must contain exactly the same poses as fPoseList; RemoveFromVSList deliberately does a linear scan rather than a binary search because the search could return a too-high index and silently fail to remove (ticket #4322 comment in the source). Poses are deleted only by DeletePose/ClearPoses; a pose deleted while it is fDropTarget, fActivePose, fSelectionPivotPose or fRealPivotPose must clear those pointers.

VIEW STATE OWNERSHIP. BViewState (fViewState) owns view mode, icon size, LastIconMode/LastIconSize, ListOrigin/IconOrigin and primary/secondary sort + reverse. It is replaced wholesale when restoring from an attribute or message, so any pointer into it must be re-read after RestoreState. fColumnList owns the BColumn objects; BTitleView holds a parallel list of BColumnTitle wrappers that must be Reset()/AddTitle()/RemoveTitle()d in step. Column offsets are never authoritative on disk: they are always recomputed from StartOffset() by walking the list (AddColumnList, AddColumn, RemoveColumn, ResizeColumn, MoveColumnTo all repeat this walk).

COORDINATE SPACES. Three coexist and confusing them is the classic bug: (1) view coordinates, (2) unscaled 32px "icon placement" space — BPose::fLocation is stored here and Location()/SetLocation()/MoveTo() apply the iconSize/32 scale, but ONLY in kIconMode; (3) list-row space, where a pose has no stored location at all and its rect is synthesised from its index (CalcPoseRectList = pose->CalcRect(BPoint(0, index*fListElemHeight), ...)). Consequently many list-mode code paths must pass an index or a running BPoint down, and icon-mode paths must not.

LAYOUT CACHES. fGrid/fOffset (from GetLayoutInfo), fIconPoseHeight (from SetIconPoseHeight), fListElemHeight, fListOffset and the fCachedIconSize memo must be refreshed together on every mode/size change; SetViewMode, InitCommon and SwitchDir all do SetIconPoseHeight() → GetLayoutInfo() → ResetPosePlacementHint() in that order. fExtent is an incrementally maintained union with an inverted-rect sentinel (INT32_MAX,INT32_MAX,INT32_MIN,INT32_MIN) for "empty"; it is only valid in icon modes (RecalcExtent/RemoveFromExtent assert ViewMode() != kListMode) because list extent is computed on demand from column widths and row count.

THREADING. Poses are produced by a separate AddPosesTask thread (spawn_thread, B_DISPLAY_PRIORITY). It reads dirents and constructs Models with the window UNLOCKED, then locks the window to call ReadPoseInfo/PoseVisible and ships chunks of at most kMaxAddPosesChunk (50) models — or whatever it has after 300 ms — to the view via a kAddNewPoses message; CreatePoses runs on the window thread. A task is valid only while its thread id is in fAddPosesThreads; SwitchDir and DetachedFromWindow clear that set to make in-flight tasks self-terminate (DetachedFromWindow then unlocks the looper and wait_for_thread()s each). All layout, drawing and scrollbar work happens on the window thread with the window locked; UpdateScrollRange explicitly takes an AutoLock<BWindow>, reads Bounds/LeftTop/Extent, and unlocks before touching the scrollbars.

DRAWING PIPELINE. Draw() → DrawViewCommon() (poses) and, when B_DRAW_ON_CHILDREN is not set, DrawAfterChildren() (the transparent selection rect, painted above replicant children). Incremental updates use CopyBits + SynchronousUpdate(rect) (Invalidate followed by Window()->UpdateIfNeeded()) rather than full invalidation — this is how row insert, row delete, column resize and pending scroll all work, and it requires that the rect arithmetic exactly match the row geometry. ColumnRedraw uses the single static shared OffscreenBitmap (sOffscreen, BeginUsing/DoneUsing) — only one pose view may use it at a time. sFontHeight, sFontInfo and sMatchString are static across all pose views.

SCROLL COUPLING. ScrollTo() is overridden to mirror the origin into the view state, so any scroll — including programmatic ones — persists. The horizontal scrollbar is a TScrollBar that also scrolls the title view. Bulk re-layout must bracket itself in DisableScrollBars()/EnableScrollBars() (targets nulled) and use SetScrollBarsTo() rather than raw ScrollTo() so the bars and the view do not fight. Some paths deliberately call _inherited::ScrollTo() to move the view WITHOUT updating the saved origin (AddPosesCompleted, DeletePose, UpdateAfterFilterChange).

PLACEMENT INVARIANT. Any code that changes a pose's location in icon mode must: RemoveFromVSList → change location → AddToVSList, and update the extent (RemoveFromExtent old / AddToExtent new). Doing it in the wrong order corrupts the y-sorted list because AddToVSList/FirstIndexAtOrBelow key off the pose's current y. Cleanup, CheckAutoPlacedPoses, CheckPoseVisibility, MoveSelectionInto and CreatePoses all follow this sequence.
