TikuBench

View / Results report opens a formatted results snapshot in the Help reader. You can search the report and copy text. Long reports explicitly say how many result rows are shown; the full results and log remain in Bench. Opening a report never starts tests, flashes firmware or reconnects a device.

Bench runs TikuBench's test suites against a board connected to this desktop and shows what came back. The Deskbar leaf offers it under Device Tools as TikuBench. The window it opens is named Bench, and it puts two menus on the top bar: Bench, and a View menu whose rows are the eight tabs and, beneath them, Results report….

The window has two parts. Down the left is a column of cards about the board and the run: Device, Kernel history, Connection, Build mode, Options, ePaper kit and Make, with Run selected and Stop under them. These stay in view whatever you are looking at. The window grows by its bottom-right corner; the views take the room and the cards keep their column, and it never shrinks below the size it opened at. To the right, over the tabs, three pills count the groups that passed, failed and did not run, a word says whether Bench is idle, reading the catalogue, running or finished, and a bar shows how far the queue has got. The tabs under them are Suites, Results, Output, Console, History, Benchmarks, Did not run and Firmware.

What it needs

The tests, the catalogue and the runner stay in TikuBench. Bench looks for a folder named TikuBench beside the applications folder this desktop was built in, and reads the catalogue by running TikuBench's own Python metadata reader there. Another checkout can be named outright with the TIKU_BENCH variable. With no checkout, or no Python behind it, the note line at the foot of the window says the metadata failed and Run selected stays disabled.

Refresh beside the filter, and Refresh catalogue in the Bench menu, read it again.

Choosing a device

Connect a board first from the Devices menu on the top bar, as Devices describes. The list in the Device card holds the boards mounted on this desktop. Before anything is chosen Bench uses the current device; once you pick a board it keeps that one, and a board that goes away is never silently replaced by another. Under the list the card prints the profile Bench will run under and either Monitor only or Build + flash. The Kernel history card under it is the verdict for that profile: the latest full run's result and age, UNPROVEN when the profile has no full run and STALE when that run is older than 24 hours, then the latest selected and diagnostic results and a performance word folded from the benchmark records.

Suites and tests

The Suites tab lists every suite in the catalogue with its sub-tests under it, under a heading for each group the catalogue puts them in. The disclosure arrow or Return expands a suite, or folds a group under its heading; a checkbox or Space selects. The Filter field matches a suite's key, name and group and a sub-test's id and label, and while it holds text the matching children are shown expanded.

Selecting a whole suite runs that suite in full. Selecting sub-tests instead runs them as one --only argument. Selected suites run one after another in the order the catalogue lists them.

A sub-test drawn in red is destructive: it may erase every file in /data on the board. A full sweep never includes one. When you select one yourself, Run selected asks about it on its own before the run's question, with Cancel as the default, and the runner is told to allow it for that run only; the next run asks again. Use a scratch board.

A suite the chosen board does not support is drawn dim and cannot be checked. When a suite is highlighted the line under the list shows its description. When a sub-test is highlighted it shows the sub-test's group and kind, then whether it belongs to a full sweep, is reachable only by selecting it, or why it is excluded. All (Select visible in the Bench menu) selects every displayed suite the board supports, each in full. None drops every selection, including those hidden by the filter. Changing the device, the memory model or the USB console setting also clears the selection.

The Did not run tab lists every sub-test the chosen board's profile leaves out, each with the catalogue's reason, so that what a full sweep never touched is on record and not merely absent.

The run options

The cards under Kernel history hold the options a run is started with.

  • Connection shows the port the device is on and holds the Baud field. The baud must be digits only, from 1200 to 4000000. A value outside that starts no run: the note line asks you to check baud, port and KEY=VALUE tokens, and the field takes the focus. It is disabled while the USB console is on, because the runner then finds the port itself.
  • Build mode is two radio buttons. Monitor existing firmware is where Bench starts: the runner is told to skip the build. Build + flash, then monitor builds and flashes, which replaces the firmware on the board. A test can still reset the board or write its storage either way.
  • Options holds four checkboxes. MSP430 large selects the large memory model and RP2350 USB the USB console, and each can be set only for a board whose catalogue entry allows it. CRACEN PK adds TIKU_CRACEN_PK_ENABLE=1 and ePaper kit adds HAS_TIKUKITS=1 and TIKU_KIT_EPAPER_ENABLE=1 to the make variables.
  • ePaper kit wakes with that checkbox: the Panel and Pattern lists choose the kit's panel and test pattern, and become EPAPER_KIT_PANEL and EPAPER_KIT_PATTERN defines ahead of the extra C flags.
  • Make holds two fields. Vars takes whitespace-separated KEY=VALUE tokens with no shell quoting; a MEMORY_MODEL token is refused, use the checkbox. CFLAGS is passed to the runner as one extra-cflags argument.

The options, the device and the presets are remembered in ~/.config/tikubench-desktop/settings, a key=value file written whenever one of them changes and read when Bench starts. A remembered board that is not mounted at start is waited for: the current device runs meanwhile, and the remembered one is chosen when it appears. The environment variable TIKU_BENCH_SETTINGS names another file.

Running

Run selected is enabled only once the catalogue has loaded, the board is supported and something is selected. It opens a confirmation naming the number of suites, the device, the profile and the mode, and warning that the desktop will release its connection until the queue finishes. Its two buttons are Cancel and Run tests. Cancel is the default: Return takes the default and Escape cancels, so a run begins only when you move the default with Tab or press and release the pointer on Run tests.

On Run tests Bench checks that the device's port and MCU are still the ones named in the confirmation. If they changed, nothing runs and the note line says to select and review the device again. Otherwise the desktop hands the serial port over for the whole queue and the window changes to Results.

Results and output

  • Results lists a row for every planned test. The pills over the tabs count the groups that passed, failed and did not run, and the bar under them fills as groups complete; the pills are grey until a run gives them a colour. A test that asserted nothing is a skip, not a pass. A missing completion marker or a runner that exits badly is a failure.
  • Output is the test output with the build and flash lines, the lines carrying [TC:] completion markers and the runner's arguments taken out. Console is everything the runner printed, with the arguments each suite was started with. The two tabs share one ring of the latest 256 lines, which Output then filters; the whole run is in the log file. Scrolling with the wheel stops the view following, and Follow tail in the Bench menu starts it again. Under the list, Copy log copies the kept lines and Clear view empties both Output and Console without touching the log.
  • The field under the list and Send feed a line to a suite that asks for one, and work only while a run is under way. A suite that needs a board unplugged or reconnected says so in bold above the note line.
  • History and Benchmarks show the records TikuBench kept for the current profile; the verdict itself is the Kernel history card. A benchmark comparison is not a test verdict.

Each run writes its own log under /tmp. Open full log in the Bench menu opens it through the desktop, and copies its path when it cannot. A log worth keeping has to be copied out, because the system is free to clean /tmp.

Stopping and the device

Stop interrupts the runner and kills it if it has not gone two seconds later. Closing the window while a run is under way stops it first, then closes. When the queue ends the desktop takes the device back; if it does not return, the note line says to reconnect it in Devices.

Installing firmware

The Firmware tab builds and installs firmware for the chosen board with TikuBench's tikubench firmware, which takes its options from the tikuOS Makefile itself, so the tab never holds a copy of them. Its first line says what the board runs now: the build the image names (its commit, with a + when the tree differed from it, and a checksum of its options) and the board it was built for.

Preset chooses the starting point: the shell, the shell with BASIC, with the init system or with the network stack, the board's own radio or accelerator image, or the kernel alone. A preset the Makefile refuses for this part is listed but cannot be chosen, and its reason shows beside the list. Under it are the options that apply to this part, grouped as the Makefile groups them. A checkbox flips a switch, and each change goes with every run as --set NAME=VALUE; Extra takes more KEY=VALUE words, for the options that hold a value.

Preview hands the board to the tool, which reads what the board runs, builds the image and says what the update does to the values the board keeps across updates, its name, aliases and boot count among them. Then it hands the board back; nothing is flashed. Install… does the same and then asks, the preview in the question and Cancel the default; only Install flashes. The tool refuses to build when the board answers as another part, or runs an image built for another board. It flashes a J-Link board through its own probe without opening a window, a Nordic part never through nrfutil, and an Apollo510 only after its eMMC and PSRAM are down. Afterwards it reads the board back, and the install fails unless the board runs the new build with its file store ready. The pills Check, Build, Flash and Verify show where it has got, and the line under them what the board runs before and after.

Stop stops a preview or a build, but not a flash under way: a part cut off mid-write is left half-programmed, so that step runs to its end. MSP430 boards are built but not flashed on macOS; flash main.elf with UniFlash. The kernel-only preset leaves no shell, so nothing talks to the board again until a shell image goes back on through its probe. Preview firmware and Install firmware… in the Bench menu do what the buttons do, and Update… beside the installed build in Devices Preferences opens this tab for that board.
